          Relations: Aggregate on (stitchline.orders_sharded_p0 orders_sharded)

    ->  Async Foreign Scan
          Output: orders_sharded_1.customer_id, (count(*)), (sum(orders_sharded_1.total_amount))

==============================================================================
S5  Query WITHOUT the shard key: find one order by its number
==============================================================================
  Append
    ->  Async Foreign Scan on orders_sharded_p0 orders_sharded_1
    ->  Async Foreign Scan on orders_sharded_p1 orders_sharded_2
    ->  Async Foreign Scan on orders_sharded_p2 orders_sharded_3
    ->  Async Foreign Scan on orders_sharded_p3 orders_sharded_4
  → every shard must be asked (and order_number has no index on the shards)
  → uniqueness of order_number across shards can NOT be enforced by the database:
    each shard only knows its own rows, so a global UNIQUE constraint is impossible here

==============================================================================
S6  Cross-shard write: move a customer's order between shards with TWO-PHASE COMMIT
==============================================================================
  order 1 must move from shard1 to shard2 (e.g. after re-sharding). Both writes must happen, or neither.
  phase 1: both shards PREPARED (each has promised it can commit)
  -- coordinator crashes here, before sending COMMIT PREPARED --
  shard1: pg_prepared_xacts → ['move_order_1_shard1'] (survived the session ending)
  shard2: pg_prepared_xacts → ['move_order_1_shard2'] (survived the session ending)
  shard1: another session tries to touch order 1 → ERROR canceling statement due to lock timeout
          (the prepared transaction still holds its locks: 2PC BLOCKS until someone decides)
  phase 2: COMMIT PREPARED on both → order 1 on shard1: 0, on shard2: 1  (moved exactly once)
  note: postgres_fdw on its own does NOT use 2PC; a crash between the two remote commits
        could leave one shard committed and the other not
